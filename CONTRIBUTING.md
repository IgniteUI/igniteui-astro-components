# Contributing

This package is the shared UI for the Infragistics documentation sites. Changes
here reach [igniteui-documentation](https://github.com/IgniteUI/igniteui-documentation),
api-docs and the blog only after a release, so the bar is: every change is
visible in the playground, documented in the component's README, and does not
break a consumer that upgrades.

If you are an AI agent, `AGENTS.md` is the short version of this file.

## Setup

- Node 22.12 or newer (CI uses 24) and npm.
- `npm ci` installs dependencies and, through the `prepare` script, the husky
  pre-commit hook.
- There is no build. `src/` is published as-is; the playground compiles it the
  same way a consumer does.

## Playground

`npm run playground` starts an Astro site on http://localhost:4567 that renders
every component in isolation. It does not use the package's integration:
`playground/astro.config.mjs` stubs the two virtual modules and
`playground/src/middleware.ts` provides the `Astro.locals` a host must set. Use
it as the reference for wiring a new consumer. See
[playground/README.md](playground/README.md) for the page list and how to add a
page.

## Tests

`npm test` runs two suites:

- `npm run test:components`: Vitest over `tests/components/**/*.test.ts`, one
  file per component, rendered with Astro's container API against the virtual
  module stubs in `vitest.config.ts`. This is where a component test goes.
- `npm run test:scripts`: `node --test "scripts/**/*.test.mjs"` for
  script-level modules transpiled on the fly under JSDOM
  (`scripts/sample-widget.test.mjs` is the pattern) and `scripts/llms.test.mjs`,
  which keeps the agent-facing docs honest (see below).

`npm run playground:check` runs `astro check` over the playground only
(`playground/tsconfig.json` includes `playground/src`, not `../src`). Nothing
type-checks `src/` yet: widening the include reports 21 errors, among them
#161, so it is a follow-up.

## Lint, format and the pre-commit hook

- `npm run lint` runs oxlint; `npm run format:check` runs Prettier.
- The husky pre-commit hook runs lint-staged: `oxlint --fix` on scripts and
  `.astro` files, `prettier --write` on those plus JSON, Markdown, SCSS and
  YAML. Only staged files are touched. `.txt` files have no Prettier parser and
  are left alone, which is why `llms.txt` keeps its long lines.
- `.git-blame-ignore-revs` lists the repository-wide formatting commits;
  configure `git config blame.ignoreRevsFile .git-blame-ignore-revs` once.

## Component anatomy

Each component is a folder:

```
src/components/<Name>/
  <Name>.astro      interface Props at the top, one JSDoc line per prop
  <Name>.scss       imported by the component; tokens as --igd-* custom properties
  README.md         see template below
```

The `Props` rule applies to components you add or change; 6 of the 28 `.astro`
files follow it today, and the rest are brought in line when they are touched.
MDX content components live under `src/components/mdx/<Name>/` and are
exported as `./components/mdx/<Name>.astro`. The public surface is
`package.json#exports`: a file that is not listed there cannot be imported by a
consumer, so add the subpath when you add a component. Then add a row to the
tables in `README.md`, a line to `llms.txt`, a playground page and a test in
`tests/components/`.

README template:

```md
# <Name>

One paragraph: what it renders and when to use it.

## Import

import <Name> from 'igniteui-astro-components/components/<Name>.astro';
(MDX components: 'igniteui-astro-components/components/mdx/<Name>.astro')

## Props

| Prop | Type | Default | Description | (every prop in `interface Props`)

## Slots (if any)

## Example (a complete, copy-pasteable usage)

## Behaviour (events, data attributes, keyboard, what runs client-side)

## Styling (the --igd-* tokens it reads)

## Host requirements (Astro.locals, virtual modules, peer components it needs)
```

State the host requirements explicitly: which `Astro.locals` the component
reads, whether it imports the virtual modules, and whether it needs
`igniteui-webcomponents` elements registered.

## Docs for AI agents

- `llms.txt` is a hand-written index: one line per export with its props and a
  link to its README. Edit it when you add, rename or remove an export or a
  prop. It ships in the npm package, so consumer-side agents read it from
  `node_modules`.
- `llms-full.txt` is generated by `scripts/build-llms.mjs` from `llms.txt`,
  `package.json#exports`, `README.md` and every `src/**/README.md`. It is not
  committed: `prepack` builds it, so it is in the published package, and
  `npm run build:llms` writes it locally for inspection. (A committed copy
  went stale whenever the pre-commit hook re-aligned a README table after the
  file was built.)
- `scripts/llms.test.mjs` fails when an export is missing from `llms.txt`,
  when a README is not linked, when a link is broken, when an exported
  `.astro` component has no README, or when the build throws.
- `AGENTS.md` (read by Claude Code through `CLAUDE.md`, and by Codex, Copilot
  and Cursor directly) holds the rules an agent needs in context. Keep it short;
  put explanations here.

## Filing issues

Use the issue forms on GitHub:

- **Bug report** (`[Bug]: `, label `:bug: bug`): what happened, steps, where you
  saw it (which site and page), optional component and version.
- **Feature request** (`[Feature]: `, label `:screwdriver: enhancement`): the
  problem and a proposal.
- **Accessibility** (`[A11y]: `, labels `:wheelchair: a11y` and `:bug: bug`).

Add a `Component: <Name>` or `Area: <area>` label when you can. Problems with
the _content_ of a docs page belong in igniteui-documentation; this repo owns
only the components and styles.

## Pull requests

- Branch `<user>/<topic>` from `master`; Conventional Commit messages with a
  scope (`feat(sample):`, `fix(styles):`, `docs:`, `chore(github):`).
- Fill in `.github/PULL_REQUEST_TEMPLATE.md`. A CI check ("PR template")
  requires a non-empty **Summary**, a **Related issue** line (`Closes #123`,
  `Part of #123`, or `No issue`), at least one ticked **Type of change** box,
  and a **Consumer impact** section whenever "Breaking change" is ticked. The
  other sections (How to test, Screenshots, Notes for the reviewer) are
  optional but make review faster.
- CI runs `npm run format:check` (first, so a formatting miss fails before the
  tests), `npm test`, `npm run lint`, `npm run playground:check`,
  `npm run playground:build` and CodeQL. PRs are squash-merged.

## Releases

1. Merge to `master`.
2. Create a GitHub Release with a tag of the form `1.7.0` (no `v` prefix; the
   workflow strips one if present). Write the consumer-facing notes in the
   release body, because there is no CHANGELOG file.
3. The **Release** workflow checks out the tag, sets `package.json#version` from
   it (the committed version is a placeholder) and runs
   `npm publish --provenance`. It can also be dispatched by hand with a tag.

Consumers pin a version and upgrade on their own schedule; a release does not
change any site until its `package.json` is bumped.

## Testing against a consumer

Point the consumer at your checkout instead of the registry:

```json
{ "dependencies": { "igniteui-astro-components": "file:../astro-components" } }
```

`npm install` then creates a symlink in `node_modules`, so every save is
visible immediately. Two caveats:

- the installed "version" is whatever your branch has, not a published tag;
- Vite 8 enforces package exports through symlinks, so the consumer may need
  `vite.resolve.preserveSymlinks: true` (igniteui-documentation's Angular
  config does this).

A `tsconfig` path alias is the no-install alternative; see
[README.md](README.md#using-from-another-repo-without-publishing-a-package).
